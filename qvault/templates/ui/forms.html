{# Form controls (styles: components.css, "forms"). Every control has a visible label tied to it; a caption and an error are tied to it with aria-describedby, and an error sets aria-invalid. The field names are the ones the routes read, so a converted form posts exactly what it did. field(name, label, type='text', value=None, caption=None, error=None, required=False, id=None, attrs={}, suffix=None, mono=False) type any input type, or 'textarea'. suffix a unit drawn inside the right edge of the input ("ETH"); not part of the value. mono set the value in the mono face: for an address or a hash, never for prose. error a message or a list of messages (a WTForms field's .errors works as is). id defaults to 'f-' ~ name. select(name, label, options, selected=None, caption=None, error=None, id=None, attrs={}, inline=False) options a list of (value, text) pairs; selected is compared as a string. inline for a toolbar filter: the label is read but not shown (the first option names the filter, "All vaults"), and the field takes no bottom margin. due_field(name, label, value=None, caption=None, error=None, min=None, max=None, id=None, empty='No due date') A due date and time, in UTC, without the browser's native date control. It is a text input a person can type "2026-10-13 17:00" into (the form reads that format and the native one), with a calendar button: qvault.js opens a month grid and a time list and writes the input, and reads the chosen moment back in words under the field ("Tue 13 Oct 2026, 17:00 UTC, in 7 days"). min and max (datetimes) bound the calendar; the route refuses a past due time and a payment's longer than 30 days. empty is what the read-back says while the field is blank. Elements anywhere on the page marked data-due-echo="" show the same words (the "who approves" preview). The calendar button is drawn hidden and qvault.js shows it, so without the script there is no dead button. date_field(name, label, value=None, caption=None, error=None, id=None, bad=False) A calendar day, "YYYY-MM-DD", for a filter. Like due_field it is a text input with a calendar button and no native date control, so it posts the same string a native date input posts, typed or picked. Picking a day writes the input and fires change (a data-autosubmit form submits on it); a value that is not a date says so under the field. bad the route refused value as not a day (a hand-made URL, or a form sent without the script): it is shown as typed, marked invalid, with the same words qvault.js uses. number(name, label, value=None, min=None, max=None, step=None, caption=None, error=None, required=False, id=None, attrs={}, inline=False) A whole number. The input stays a native type="number" (arrow keys, a spinbutton for screen readers, the numeric keypad on a phone, min and max checked by the browser); qvault.js swaps the browser's tiny spinner for − and + buttons that stop at min and max. The buttons are out of the tab order because the arrow keys already do what they do. inline the label is read but not shown, for a toolbar. file_drop(name, label, caption=None, error=None, id=None, accept=None, max_bytes=None, required=False) A file input drawn as a drop zone: "Choose a file or drop it here", then the chosen file's name and size. The input itself stays in the page (visually hidden, still focusable), so it posts exactly as before and works without JavaScript; qvault.js adds the drop and the name. accept the input's accept list; a dropped file must match it too (the file dialog filters, a drop would not). max_bytes the server's limit for this file. qvault.js refuses a larger file before upload and says why; the route still enforces its own limit, this only saves the wait. Only one file: a drop of several is refused rather than silently posting the first. search(name, label, value=None, placeholder=None, id=None) A search box for a toolbar, with its magnifier drawn inside. The label is read, not shown. checkbox(name, label, checked=False, value='1', caption=None, id=None, attrs={}, disabled=False) switch(name, label, checked=False, value='1', caption=None, id=None, attrs={}, disabled=False) A switch is a checkbox with role="switch": it posts the same way, and applies a setting rather than agreeing to something. value is what a ticked box posts: keep the one the route reads ("on" for a bare HTML checkbox, "y" for a WTForms BooleanField). radio_group(name, legend, options, selected=None, error=None) options a list of (value, text) or (value, text, caption) tuples. wtf_field(f, caption=None, attrs={}, mono=False, aside=None) A WTForms field drawn as a field: the same label, caption and error as field(), but the input is the form's own rendering, so its id, name, value and the validators' attributes (required, maxlength) are exactly what the form declares.
