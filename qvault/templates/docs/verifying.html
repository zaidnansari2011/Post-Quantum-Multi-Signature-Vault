Any decision can be exported as a single file that someone outside this organisation can check without an account, without a network connection, and without taking our word for anything. On a decision page, use Export for verification.

Three ways to check one

Three ways to check a decision
MethodTrusts
The verify page Drop the file in. No account needed. This server. Convenient, but it is the same server that produced the file, so it is a convenience rather than evidence.
python -m qvault.verify Exit code 0 verified, 1 not verified, 2 unreadable. Nothing of ours at run time. Suitable as a gate in a pipeline.
The offline verifier One HTML file. Save it, open it anywhere. Nothing. It runs in the browser from a local file, with the post-quantum library bundled inside it.

What gets checked

Each step closes a gap the one before it leaves open, so the order is the argument:

  1. the decision text is the text that was hashed;
  2. every signature is a valid post-quantum signature over exactly that;
  3. each signer was authorised when the decision opened, not merely a member today;
  4. the approval rule frozen at that same moment was satisfied;
  5. for a payment, each approver's authorisation to pay is over exactly that payment, and is the one the record logged; a payment the record says was made is backed by enough of them;
  6. the audit record's own entries for these events recompute;
  7. those entries name these exact signature bytes, and no others;
  8. the signers are the accounts the record registered;
  9. those entries are provably inside a published Merkle tree;
  10. that tree's root is signed by the log;
  11. and countersigned by an independent witness.

Steps 1 to 4 are what an ordinary "export the signatures" format gives you, and they are worth less than they look: whoever builds the file chooses what goes in it, so they could omit an inconvenient rejection, or export a decision that never happened. Steps 6 to 11 are what stop that. The last one is the only step that still holds if the operator of this system is the one you are checking up on.

Pinning the keys

A bundle names its own keys, so on its own it proves only that some log signed it. To make it prove that this log signed it, get the fingerprints from somewhere other than the file (they are on Audit → Transparency, and the witness prints its own on startup) and require them: 

python -m qvault.verify decision.qvault.json \
    --expect-log 4f2a9c1e77b30d85 \
    --expect-witness 8c1d05fa2b6e4470

The log's public signed head

Anyone can fetch the log's signed head without an account. It holds the newest head the log signed and the newest one a witness co-signed, each with its signatures and key fingerprints, and nothing about any person, vault or decision. The two differ while the witness hasn't yet seen the newest entries. 

python -m qvault.verify checkpoint.json --expect-log 4f2a9c1e77b30d85

This checks the log's signature on each head and every witness co-signature in the file. It can't prove the newer head extends the witnessed one; the witness checks that before it co-signs. Its main use is the fingerprints: read from this server's public address, they are the values to pass as --expect-log and --expect-witness when you check a decision.

Algorithms the browser cannot check

The offline verifier checks ML-DSA-65 and ML-DSA-87. It does not check SLH-DSA, because the implementation here is the SPHINCS+ round-3 submission and the browser library implements FIPS 205, which is derived from it but not byte-compatible. Rather than report genuine signatures as forged, the page marks those as un-checkable and points at the command line, which uses the same implementation that produced them.
