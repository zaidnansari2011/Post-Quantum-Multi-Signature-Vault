The encryption protecting most systems today relies on problems that are slow for an ordinary computer and fast for a large enough quantum one. That is not only a future concern: an attacker can copy encrypted data now and decrypt it years later. Anything that must stay private or provable for a decade is already exposed.

In August 2024 NIST published the first replacement standards. Q-Vault uses all three.

What is used where

  • ML-DSA (FIPS 204) — signatures. Every approval, and the seal over the audit record.
  • ML-KEM (FIPS 203) — key encapsulation. Wraps the AES key of every file stored in a vault.
  • SLH-DSA (FIPS 205) — a hash-based signature alternative, available as a switchable option.

What it costs

Post-quantum cryptography is affordable in time and expensive in space. Measured on the development machine, against classical schemes measured the same way:

SchemeSignVerify Public keySignature
RSA-2048 classical 0.53 ms0.03 ms294 B256 B
ECDSA P-256 classical 0.04 ms0.08 ms91 B71 B
ML-DSA-65 1.71 ms0.63 ms1,952 B3,309 B
SLH-DSA-SHAKE-256f 38.66 ms1.77 ms64 B49,856 B

ML-DSA's signature is about 13× RSA's. SLH-DSA's is roughly 195× — but its public key is 64 bytes, less than a quarter of RSA's, and its security rests on nothing but a hash function rather than on any structured mathematical assumption. That trade is why both are standardised, and why being able to move between them matters.

Changing algorithm

Every key, signature and seal records the algorithm that produced it, and is always verified by that same algorithm. Switching the system default therefore changes only which algorithm new keys use. Everything already signed keeps its own and stays valid — nothing is re-signed, and the stored signature bytes do not change.

The practical consequence is that the system deliberately runs a mixed set: existing keys on one algorithm, new keys on another, all verifying. When an algorithm is eventually weakened, replacing it is a configuration change rather than a rebuild, and no history is lost.

Moving to a weaker algorithm is treated differently from moving to a stronger one. A decrease in NIST security category is refused unless it is explicitly confirmed with a stated reason, and it is recorded as a distinct downgrade event so an auditor can find every weakening decision by event type alone.
