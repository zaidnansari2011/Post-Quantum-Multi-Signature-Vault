Every action in Q-Vault is appended to a single record: registrations, vaults, membership changes, proposals, signatures, key replacements, algorithm changes. It is the product's memory, and it is built so that altering it shows.

The chain

Each entry stores a SHA-256 hash of its own contents and the hash of the entry before it. That makes the record a chain: recompute any entry and its hash no longer matches, so verification reports a break at exactly that point, and every entry after it becomes unprovable.

The seal

A chain alone only catches a careless edit. An attacker with database access could rewrite an entry and recompute every hash after it, leaving the chain self-consistent again.

So the end of the record is signed by a key belonging to the system itself. A consistent rewrite changes the final hash, which the existing signature no longer covers — and producing a new one requires a private key the attacker does not have. The signing key is owner-less, wrapped under the server's master key, and its public half is MAC-bound to that master key, so a substitute key cannot be injected either.

The witness

The seal still leaves one gap, because it lives in the store it protects: an adversary who deletes the tail of the record and its seals is left with a shorter record that is perfectly self-consistent. Nothing inside the system can notice, because there is nothing inside the system left to compare against.

So the record is also published as a Merkle tree, and a separate service — with its own key, its own storage, and no access to this database — countersigns each published root. It keeps the size and root of the last one it signed, and it will only sign a new one that provably contains that earlier one. Delete entries and the log can no longer produce that proof, so it stops being countersigned, and the attempt is recorded on the witness's side.

Audit → Transparency shows the published roots, the witness, and the gap between the newest root and the newest one countersigned. A gap that stops closing while entries keep arriving is what a rewrite looks like from the outside.

What it does not defend against

Immutable is the wrong word. An adversary with raw database write access can rewrite the chain. What they cannot do is produce a seal that matches, a countersignature from a key they do not hold, or a consistency proof for a history they have edited.

The remaining assumption is the witness's independence. Run on the same machine, under the same operator, it demonstrates the mechanism without delivering the security — whoever can rewrite the database can also stop the process and delete its file. The guarantee is worth exactly as much as the separation is real.

What you can see

The audit view is scoped: you see events for vaults you belong to, your own actions, and global system events. Integrity, however, is always verified over the whole chain, not the part you can see — a page of entries cannot tell you whether the record is intact.

Filters narrow what is displayed and can never widen it. The CSV export runs through exactly the same scoping as the screen.
